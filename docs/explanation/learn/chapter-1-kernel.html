Tôi ra lệnh, có thứ thi hành

Nhu cầu: tôi muốn nói "chạy tool X" và có một thứ đáng tin nhận lệnh, thực thi, trả kết quả — kể cả khi tool đó hỏng. Nhu cầu này đẻ ra AgentKernel + execute_tool.

§Câu đố

đoán trước khi lật
Tool có thể lỗi: file thiếu, network chết, bug. Nếu một tool ném exception, chuyện gì xảy ra với cả agent?
Không sập gì cả. Kernel bọc try/except quanh executor (core/kernel.py:113): một tool ném exception thì lỗi bị bắt và biến thành envelope kernel_error — agent vẫn sống, vẫn nhận được kết quả "thất bại có cấu trúc".

Đây là lý do mọi tool đi qua một cửa: cửa là nơi duy nhất đặt cái lưới an toàn đó. Tool nằm rải rác thì mỗi tool phải tự lo try/except — sẽ có chỗ quên.

⌥Slice — vì sao config bị đông cứng?

deep_freeze: kernel dùng chung thì config phải bất biến

Kernel là shared — nhiều session (nhiều run) dùng chung một kernel. Nếu config còn sửa được, một run lỡ ghi đè config thì các run khác bị ảnh hưởng → state rò giữa các run. Vì vậy freeze() biến config thành read-only bằng MappingProxyType (core/kernel.py:14-21,48-54).

# minh hoạ tối giản — chạy: python3 -c "..."
from types import MappingProxyType
cfg = MappingProxyType({"model": "gpt-4o"})
cfg["model"] = "khác"   # thử ghi đè
# TypeError: 'mappingproxy' object does not support item assignment

Một cửa = một nơi để khoá. Đông cứng ở cửa thì mọi run sau đều an toàn, không phải tin từng tool.

⊞Đằng sau cửa — registry & envelope

Thiếu tool thì sao? resolve_tool trả về NullToolPort — một executor "rỗng" trả lỗi missing_capability thay vì để kernel chết (core/registry.py:29-40,103-112). Cửa luôn có thứ để gọi.

Envelope chuẩn: mọi kết quả được gói thành CapabilityResult với đúng các khoá ok · capability · feature · data · error · metadata (core/schemas.py:63-111). Caller chỉ cần biết một hình dạng, không cần biết tool nào trả gì.
